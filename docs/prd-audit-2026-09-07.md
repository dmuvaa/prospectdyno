# ProspectOS PRD Audit

Date: 2026-09-07
Project audited: `/Users/la/prospectdyno`
PRD version: AI Prospect Intelligence & GTM Platform v1.0

## Executive Summary

The project is a legitimate internal-alpha implementation of the ProspectOS idea, currently branded `ProspectDyno`. It already has the core product spine:

```text
Supabase Auth -> workspace -> ICP builder -> search job -> company ingestion ->
website audit -> AI qualification -> opportunity feed -> list/export/message draft
```

It is not yet production SaaS or private-beta ready. The biggest gaps are not in the UI shell; they are in durable background infrastructure, idempotent metering/credits, richer canonical data modeling, research-agent observability, campaign/outreach primitives, storage, realtime, and operational security.

High-level readiness:

| Area | Readiness | Notes |
| --- | ---: | --- |
| Sprint 1 foundation | 70% | Supabase, auth, RLS, workspace, dashboard, ICP builder exist. |
| MVP product loop | 45% | The ICP -> search -> opportunity loop works in simplified form. |
| Production SaaS readiness | 20% | Missing durable queue, billing, API keys, tests, monitoring, storage policies. |
| PRD full vision | 15% | Campaigns, inbox, CRM, continuous discovery, learning loop mostly absent. |

## What Exists

### Application Structure

The repo uses Next.js 16, TypeScript, Tailwind CSS 4, and workspace packages:

- `app/` for dashboard pages and route handlers.
- `components/` for UI and feature components.
- `lib/` for server actions, workspace helpers, API auth, jobs, and pipeline logic.
- `packages/supabase` for browser/server/admin clients and DB types.
- `packages/ai` for OpenAI/OpenRouter routing and structured JSON tasks.

- `packages/shared` for shared product types, statuses, and credit constants.
- `supabase/migrations` for the schema and RLS policies.

This roughly matches the PRD's recommended modular repository direction, although it is still a single Next app plus packages rather than `apps/web`, `apps/worker`, and `apps/api`.

Good alignment:

- `auth.users -> profiles -> workspace_members -> workspaces` exists.
- Most major entities include `workspace_id`.

## Critical Findings

### 1. Worker endpoint is public when `WORKER_SECRET` is unset

File: `/Users/la/prospectdyno/app/api/jobs/process/route.ts`

The route only enforces authorization when `WORKER_SECRET` exists. If the env var is empty, anyone who can reach `POST /api/jobs/process` can process pending jobs or pass a `jobId`. That triggers service-role code.

Impact:

- External callers can burn API credits/cost.
- Jobs can be executed at unexpected times.
- Failed or repeated execution can corrupt status/cost data.

Recommendation:

- Require `WORKER_SECRET` in all non-local environments.
- Return `500` or `401` when missing.
- Prefer removing the public route once Render workers/BullMQ are in place.

### 2. Job claiming is not atomic

Files:

- `/Users/la/prospectdyno/worker.ts`
- `/Users/la/prospectdyno/app/api/jobs/process/route.ts`
- `/Users/la/prospectdyno/lib/pipeline/run-search.ts`

Both the worker and route select pending jobs, then call `processJob`. `processJob` updates status to `running` after reading the row, but does not claim only when status is still `pending`.

Impact:

- Two workers can process the same job.
- Retries can duplicate companies, contacts, opportunities, evidence, and usage events.
- Credit deductions can double-charge.

Recommendation:

- Add an atomic `claim_next_job()` database function using `for update skip locked`, or move to BullMQ.
- Make `processJob` refuse non-pending jobs unless explicitly retried.
- Add unique/idempotency keys per pipeline stage.

### 3. Usage metering is not idempotent enough for retries

File: `/Users/la/prospectdyno/lib/pipeline/run-search.ts`

`recordUsage` includes `Date.now()` in the idempotency key, which guarantees a unique key every run. That defeats the PRD requirement that expensive actions be idempotent.

Impact:

- Retries charge again.
- Race conditions charge again.
- Unit economics become untrustworthy.

Recommendation:

- Use deterministic keys such as `website_analysis:{searchId}:{companyId}`.
- Store provider cost, AI tokens, duration, job ID, model, and external run IDs.
- Use `upsert`/`on conflict do nothing`.

### 4. Credit deduction is not atomic and has no preflight budget gate

File: `/Users/la/prospectdyno/lib/pipeline/run-search.ts`

The pipeline accumulates `totalCost`, reads current workspace credits, and writes the decremented balance at the end.

Impact:

- Concurrent jobs can overwrite each other's credit changes.
- Work can continue after credits are exhausted.
- Search cost and usage events can diverge.

Recommendation:

- Add a transaction/function like `consume_credits(workspace_id, idempotency_key, amount, metadata)`.
- Check budget before expensive provider/AI calls.
- Record credits and USD separately.

### 5. Current queue strategy is alpha-only

File: `/Users/la/prospectdyno/lib/jobs.ts`

`enqueueJob` uses Next.js `after()` to call `processJob` after request handling, and README says this overlaps with the optional worker.

Impact:

- Long-running research is still tied to web runtime behavior.
- No retry/backoff/concurrency/rate limiting.
- Not suitable for Render worker + Redis/BullMQ architecture in the PRD.

Recommendation:

- Use BullMQ with Redis/Render Key Value for delivery.
- Keep Supabase as system of record for job state.
- Have workers claim/update Supabase records with idempotent transitions.

### 6. Research/evidence system can still hallucinate

Files:

- `/Users/la/prospectdyno/packages/engine/src/crawl.ts`
- `/Users/la/prospectdyno/packages/ai/src/tasks/qualify-company.ts`
- `/Users/la/prospectdyno/lib/pipeline/run-search.ts`

The AI qualifies from a single fetched page/audit summary/excerpt. Evidence source is model-supplied and may be a page type rather than a verified URL. The system stores evidence, but does not verify that a claim maps to an actual source span.

Impact:

- Product promise "evidence over assumptions" is only partially met.
- Opportunity reports may look more certain than the source supports.

Recommendation:

- Store fetched URL, HTTP status, timestamp, extracted text spans, and artifact references.
- Require evidence records to point to actual source URLs/spans.
- Separate `verified`, `inferred`, and `uncertain` evidence types.

### 7. Public API is not PRD-grade yet

Files:

- `/Users/la/prospectdyno/app/api/v1/search/route.ts`
- `/Users/la/prospectdyno/lib/api.ts`

The API uses session cookies and casts request bodies rather than validating them with Zod.

Impact:

- Not usable as a real server-to-server API.
- Weak boundary for malformed requests.
- No API key issuing, hashing, revocation, scopes, or rate limits.

Recommendation:

- Add `api_keys` table with hashed workspace-scoped keys.
- Add Zod schemas for all route inputs.
- Add rate limiting and audit logs for API calls.

## Recommended Next Engineering Plan

### Phase A: Stabilize the existing alpha loop

1. Make `/api/jobs/process` require `WORKER_SECRET` or remove it from public deployment.
2. Replace `after()` execution with a single worker path.
3. Add atomic job claiming and retry-safe job state transitions.
4. Make usage events deterministic/idempotent.
5. Add atomic credit consumption and preflight budget checks.
6. Enforce suppression records in exports and message generation.
7. Add Zod validation to API routes and server action boundaries that accept structured input.
8. Add tests for CSV parsing, domain normalization, scoring, job idempotency, usage idempotency, and workspace isolation.

### Phase B: Make intelligence trustworthy

1. Add crawl artifact storage in Supabase Storage.
2. Add `research_jobs`, `research_reports`, `agent_runs`, and `agent_steps`.
3. Store fetched URL, HTTP status, timestamp, extracted text spans, and artifact paths.
4. Split evidence into verified/inferred/uncertain claims.
5. Add score records with scoring version and configurable weights.
6. Add website crawl depth, sitemap/robots checks, structured data, internal links, and screenshot/performance analysis.

### Phase C: Complete MVP activation

1. Add `campaigns`, `campaign_leads`, `sequences`, `sequence_steps`.
2. Add message approval status, editor, prompt version, and evidence links.
3. Add contact enrichment provider abstraction and provenance tables.
4. Add export records and private export artifacts.
5. Add basic campaign UI without sending automation first.

### Phase D: Prepare private beta

1. Add integration credential model using Supabase Vault or external secrets.
2. Add email provider and webhook event storage.
3. Add reply classification and inbox.
4. Add notification records and Supabase Realtime subscriptions.
5. Add Sentry.
6. Add API keys, scopes, rate limits, and audit logs.
7. Add retention/deletion workflows.

## Overall Verdict

This is a strong alpha foundation for the first killer use cases: agency prospecting, SEO opportunity discovery, and website opportunity discovery. The project already demonstrates the right product philosophy: opportunity-first, evidence-aware, natural-language ICPs, and modular provider intent.

The next priority should not be more UI breadth. The next priority should be making the current loop durable, metered, auditable, and retry-safe. Once job execution, usage metering, evidence provenance, and storage are solid, campaigns and outreach can be added without turning the product into a fragile cold-email wrapper.
